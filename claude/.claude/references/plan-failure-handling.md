# Plan-executor failure handling

After a dispatched sub-agent returns, `plan-executor` decides whether
to mark the task complete, retry, or halt. This reference encodes the
calibration table and the audit-checkpoint flow.

See also:
- `~/.claude/references/plan-system.md` — state file location and schema
- `~/.claude/references/plan-generation.md` — Mode B generation procedure
- `~/.claude/skills/plan-auditor/SKILL.md` — the auditor invoked at
  checkpoints and at plan completion

---

## Decision flow after a sub-agent returns

- **Sub-agent reports success and produced expected deliverables.**
  Mark the task complete in the state file. Append a log entry.
  Optionally offer the user an audit checkpoint (see below).
  After marking a task complete, check whether any files committed
  in this task fall under a doc's `covers` paths (see the
  `doc-freshness` skill). If so, note in the plan log that relevant
  docs may need their `last-verified` bumped. Surface this as a
  recommendation to the user — do not bump automatically.

- **Sub-agent reports failure.** Apply the failure-calibration table
  below. Trivial → agent retries. Non-trivial → halt and ask.

---

## Audit checkpoint flow

The orchestrator invokes `plan-auditor` only on demand mid-plan, plus
automatically once at plan completion. Two checkpoint modes:

1. **Per-task checkpoint (opt-in).** After a task completes, prompt:
   "Task <id> complete. Run plan-auditor before continuing?
   (yes / no / skip-all)"
   - `yes` → dispatch plan-auditor on the just-completed task; halt
     on `fail` or `escalated` verdicts.
   - `no` → continue to the next task.
   - `skip-all` → do not prompt again for the rest of this plan run.

2. **"Audit between every task" mode.** If the user explicitly asked
   for this at plan start, set an in-memory flag and invoke
   plan-auditor after every task — still requiring explicit user
   confirmation to proceed past a `fail` verdict.

3. **Final audit (automatic).** When the last task completes, the
   orchestrator dispatches one final plan-auditor pass over the
   whole plan. The aggregated verdict gates Phase 5 cleanup: only
   `pass` or `conditional_pass` enables cleanup; `fail` or
   `escalated` leaves all artifacts in place.

Audit verdicts persist in the state file under each task's
`audit_status` field. See `plan-system.md` § State file schema for
the taxonomy.

## Failure-calibration table

| Failure type | Verdict | Rationale |
|---|---|---|
| Single test fails, fix is obvious from the error | Trivial — agent retries | Self-correctable; halting wastes a roundtrip |
| Lint/format violation | Trivial — agent retries | Mechanical; deterministic fix |
| File path or import not found in fresh agent context | Trivial — agent retries with corrected path | Often a context-load miss, not a real failure |
| Test failure with non-obvious cause | Non-trivial — halt | Risk of compounding wrong fix |
| Build error spanning multiple files | Non-trivial — halt | Cross-file blast radius needs human read |
| Auth/permission failure (push, gh) | Non-trivial — halt | Can't be fixed by retry; needs operator action |
| Agent reports "uncertain" or asks a question | Non-trivial — halt | Explicit signal — surface it |
| Deliverables missing or wrong | Non-trivial — halt | Auto-retry risks producing more wrong output |
| Audit verdict: fail | Non-trivial — halt | The audit is the calibration |

**On non-trivial failure:** halt, summarize what failed, ask the user
how to proceed (retry, skip, abort, or hand off to manual). Do not
auto-retry. Do not chain more dispatches.

**Trivial-retry budget.** A single trivial retry is allowed per task.
A second trivial-class failure on the same task escalates to
non-trivial — the calibration was wrong; surface it.

## Phase 5 cleanup gate (post-completion)

After the entire plan completes and the final auditor pass runs, the
orchestrator may offer to remove project-local execution artifacts.
The audit verdict gates this:

- `pass` or `conditional_pass` → Phase 5 may run.
- `fail` or `escalated` → skip Phase 5 entirely; leave all artifacts
  in place for the user to address.

### What Phase 5 may remove

Print a list of every artifact that would be removed before asking:

- The master plan file (only if generated by the orchestrator in Mode B)
- The tasks directory and all task files (only if generated in Mode B)
- `.claude/plan-states/<plan-name>.json`
- `.claude/plan-states/<plan-name>.log`
- `.claude/plan-completion-report.md` (offer to keep this one
  separately — often worth retaining)
- Any audit reports written during this plan

### User-authored vs orchestrator-generated

Distinguish artifacts authored by the user from artifacts generated
by the orchestrator. **Never offer to remove user-authored files.**
Mode A inputs (plan and tasks the user provided) are user-authored;
they stay. The
`artifacts_generated_by_orchestrator` flag in the state file (see
`plan-system.md` § State file schema) is the gate.

### Consent prompt

Ask verbatim:

> "Plan complete. Remove project-local execution artifacts now?
> (yes / no / keep-completion-report-only)"

- `yes` → remove all listed artifacts.
- `keep-completion-report-only` → remove everything except
  `.claude/plan-completion-report.md`.
- `no` or anything else → leave everything in place; print the
  artifact list as a record of what could be cleaned up later.

After cleanup (or skipped cleanup), print a final summary line:

> "Plan execution complete. <N> tasks executed, <N> commits made
> on branch <branch>. Cleanup: <done | skipped | partial>."

Commits made during execution are NEVER part of cleanup. Git history
is the durable record of the plan's outcome.
